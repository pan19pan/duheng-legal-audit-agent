# 01 · 产品定义与用户

## 一句话定义

给基层执法单位与法制审核环节提供**处罚决定前的合规自查**：把案卷事实读进来，
按四层审查要点过一遍，输出风险清单、处置建议与可追溯留痕。

## 用户与场景

| 用户 | 场景 | 他们真正怕什么 | 度衡给什么 |
|---|---|---|---|
| 执法办案人员 | 决定书发出前自查 | 因程序瑕疵被复议撤销、被追责 | 阻断项清单 + 补正建议 |
| 法制审核员 | 重大决定审核（行政处罚法第58条） | 案卷多、审查时间紧，漏掉硬伤 | 逐条命中理由 + 法条锚点，压缩通读时间 |
| 执法监督/案评岗 | 案卷评查、执法质量考核 | 评查标准不统一、凭经验 | 统一规则集 + 可复现的检查结果 |
| 执法对象（延伸） | 收到告知后想自查 | 不知道自己有哪些程序权利 | 案件视角的合规检查（v2 再做） |

**明确不是给谁用的**：不是给当事人写答辩状的工具，也不是自动生成处罚决定的工具。

## 待完成的工作任务（JTBD）

> "当我准备对一个非现场违法记录作出处罚决定时，我想在发出之前知道**哪些环节经不起复议诉讼**，
> 以便把瑕疵补在决定之前，而不是在复议程序里被动解释。"

## 为什么从"交通非现场执法"切入

1. **量大**：非现场执法占交通处罚大头，任何效率提升都会被放大；
2. **争议集中**：电子监控设备的合法性（审核、公布、检定）、告知时限、驾驶人识别，
   是行政复议与行政诉讼的高频撤销事由；
3. **规则相对封闭**：条款集中在行政处罚法、道路交通安全法及一部部门规章，
   适合做成规则库冷启动；
4. **领域知识可迁移**：行政执法合规的一般结构（主体、程序、事实、法律适用、裁量）
   在交通领域跑通后，可平移到市场监管等领域，规则层复用、引擎层不动。

## MVP 边界

**做**：单案件审查、四层要点、依据置信标注、待核实清单、留痕、评测脚本。
**不做**：多案卷批量（v1.5）、自动生成处罚决定书（v2，且永远只出草稿）、
处罚金额建议（只校验"在不在法定幅度内"，不给建议数额——建议数额是裁量，裁量权不能外包给系统）。

## 关键产品决策记录

| 决策 | 备选方案 | 选择理由 |
|---|---|---|
| 判定权给规则引擎，LLM 只做抽取与表达 | 端到端 LLM 直接审 | 可审计性是法律场景的入场券；幻觉在端到端方案里无法被系统性拦截 |
| 不确定 → 单列「待核实」 | 按默认值继续审 | 把 False 当成"没问题"是执法场景里最危险的静默失败 |
| 处罚金额只校验区间，不建议数额 | 给出"建议罚款额" | 裁量必须留给人；系统给区间校验与情节提示 |
| 每条依据带 high/medium 置信度 | 统一展示"依据：某某法" | 幻觉无法根治，但可以被标注与拦截 |
| 顶格处罚触发过罚相当审查 | 不做裁量层 | 复议诉讼中"过罚失当"是高频撤销事由，规则层能拦下一部分 |
