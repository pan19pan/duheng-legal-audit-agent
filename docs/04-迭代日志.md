# 04 · 迭代日志

> 记录每个版本"为什么改"，而不是"改了什么"。评测驱动的部分标注证据来源。

## v0.1 · 规则引擎骨架

- 三值逻辑表达式求值器（True / False / **None=未知**）。
- 设计动机：法律审查里最危险的失败是"把没查清当成查清了"。二值布尔会把未知吞成 False，
  三值逻辑让 unknown 显性化并归入「待核实」。

## v0.5 · 四层审查模型

- L1 形式合法性 / L2 事实认定 / L3 法律适用 / L4 裁量适当。
- 分层不是为了好看：程序瑕疵可补正、事实不清要退回、法律适用错误可能被撤销、
  裁量失当是复议诉讼高发点——四类问题的处置完全不同，混在一起报没有用。

## v0.7 · 规则外置 + 地区参数档

- 审查要点、行为→条款→罚款区间全部移入 JSON；地区参数（时效、听证门槛、法制审核门槛）单独成档。
- 动机：法律是会修的，地区是有差异的。规则必须能被法律背景的使用者直接改，
  而不是让程序员替他们改。

## v0.8 · 评测集 v1（30 例）与首轮真bug

首轮评测抓出 3 个真实缺陷，全部修在规则/引擎层：

| 缺陷 | 根因 | 修复 |
|---|---|---|
| 超速 60% 仍按低档校验罚款幅度 | 档位规则依赖的派生量在档位解析之后才写入上下文（顺序错误） | 调整引擎装配顺序 |
| "初次违法"被识别为**非**首违 | 抽取器把肯定词表误放在否定槽位 | 修正槽位 |
| 罚款 500 被误报为"顶格处罚" | 顶格判定用 `>=` 上限，把"超幅度"也当成了"顶格" | 改为 `==` |

**教训**：顶格审查和幅度校验是两条规则，语义不同，条件必须分开写。

## v0.9 · 案卷否定推定（显性化）

- 压力测试前的手工走查发现：8–13 条规则因字段缺失整体挂起，结果区被「待核实」淹没。
- 引入**案卷否定推定**：本应记载于案卷的事项（是否已罚款、有无从重情节等），未记载即推定为「无」，
  但推定字段随结果返回并在界面标注。
- 这是产品原则的一次明确取舍：**推定可以，隐身不行。**

## v0.9.2 · 压力测试暴露的两类误报（评测驱动）

压力集（8 例脏数据）首跑：结论一致率仅 37.5%。逐条归因后修了两处：

1. **规则作用域错误**：违停场景下"驾驶人不在现场"是第 93 条的处罚前提，
   却被 L2-03（身份识别）误报为缺陷。→ L2-03 排除违停，新增 L2-07（违停前置条件）。
2. **归因错误**："系统没看懂"被报成"文书没写"。→ 引入「疑似识别失败」机制：
   缺失要素若在原文中有相关表述，阻断级降为提示级，并明示"疑为识别失败，请人工核对"。

修正两处标注错误（S01、S03，详见评测报告第六节）后：
干净集 100% / 100% / 100%，压力集 召回 80% · 精确 57.1% · 结论一致 50%。

## v0.9.3 · 文案与体验

- 结果文案中的 `False/True` 改为「是/否」——执法文书语境里不该出现编程字面量。
- 支持以 `?case=DEMO-02` 直达示例，方便演示与分享。
